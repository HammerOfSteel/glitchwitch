# Character Pipeline v2 — Blender-Backed Mesh Generation — Design Spec

**Status:** Draft, pending user approval
**Supersedes (for characters only):** parts of `docs/superpowers/specs/2026-08-08-character-procedural-pipeline-design.md`
**Author context:** Glitch Witch (Godot 4, GL Compatibility renderer)

## Why this exists

The v1 character pipeline (`tools/assetgen/character_gen.py` + `part_registry.py` +
`gltf.py`) generates meshes as raw hand-rolled triangle math (boxes, cylinders, lathe
revolves) assembled into a rigid, unskinned node hierarchy. It works, is deterministic,
and is fully tested — but it structurally cannot reach the visual bar we're aiming for
(Zelda: Link's Awakening remake / Animal Crossing "toy diorama" register): no
subdivision surfaces, no bevels, no smooth-shaded rounding, no skinned deformation. A
live proof-of-concept (bevel + subsurf + shade-smooth applied to a plain cube, rendered
in the user's running Blender) confirmed the toolset gap is real and closeable — the
same primitive reads as "soft toy" instead of "flat box" with zero hand-sculpting.

Blender 5.2 is installed locally, and the user has the `blender-mcp` addon running,
giving live, watchable scripted control over a running Blender instance (a raw
JSON-over-TCP `execute` socket on `127.0.0.1:9876` that runs arbitrary Python via `exec`
inside Blender, e.g. for build/export a headless `blender --background --python
script.py` invocation is used instead — no addon/socket dependency for CI/build
reproducibility).

## Scope

**In scope:** characters only (Wren, villager, future NPCs). A hand-authored (via
scripted Blender operations, not literal mouse sculpting) generic humanoid base mesh
with proper topology and a skinned armature, checked into the repo as a static `.blend`
source asset. Archetype-specific clothing/hair/props layered on top, driven by
data/code. Animation moves from translation-keyframed rigid parts to bone-based
skinned actions. Export to GLB via Blender's native glTF exporter.

**Out of scope (future phase):** props, nature, and building assets stay on the
existing pure-Python `tools/assetgen` pipeline for now — they already meet the
"chunky toy-box" bar at their scale. Migrating them to Blender is a later, separate
phase, not part of this spec.

**Explicitly not doing:** literal manual sculpting via mouse/tablet input (I don't have
mouse control of the Blender window) — base mesh construction happens via scripted
`bmesh`/operator calls (extrude, loop cut, bevel, mirror, skin modifier, proportional
edit) that I write and run, then the result is committed once as a static asset, not
regenerated by every build.

## Architecture

### 1. Base humanoid asset (hand-authored, checked in once)

A new `tools/assetgen/blender/base_humanoid.blend`: one generic, unclothed humanoid
body with:
- Proper edge-loop topology (not primitive-stacking) built via scripted `bmesh`
  operations + a subdivision-surface modifier, so it deforms and shades smoothly.
- Chibi-adjacent proportions per the toy-diorama bar (bigger head-to-body ratio,
  rounded oversized hands/feet) — exact ratios chosen during build, validated visually
  against LoA-remake/Animal Crossing reference silhouettes.
- A real `Armature` with a joint hierarchy modeled on the proven Mixamo-style
  convention found in the user's own `HammerOfSteel/meshy` reference rigs (inspected
  directly, live, via the Blender MCP socket): `Hips` (root) → `Spine` → `Spine01` →
  `Spine02` → `Neck` → `Head`; `Shoulder` → `Arm` → `ForeArm` → `Hand` per side;
  `UpLeg` → `Leg` → `Foot` → `ToeBase` per side. We'll likely simplify the spine chain
  (fewer segments — our chunky low-poly torso doesn't need 3 spine bones) but keep the
  same naming/parenting convention since it's a well-understood, animatable standard.
  Vertex-group skin weights painted for smooth deformation (no rigid-part seams).
- UVs unwrapped onto the existing palette-atlas cell layout (`tools/assetgen/palette.py`)
  — preserves the design bible's "no painted textures, flat color cells" pillar; the
  Blender mesh still only ever samples flat palette colors, never custom painted
  textures.

This file is authored once (by me, scripted, reviewed via renders/live Blender view),
committed to git as a binary asset, and only revised deliberately (same ritual as other
design-bible-governed assets) — it is not regenerated by `make assets`.

#### Feasibility and fallback (new — was previously unaddressed)

Scripting good humanoid topology purely via `bmesh`/operator calls (no mouse-driven
sculpting) is a genuinely hard 3D modeling problem, not a routine one — flagged
explicitly rather than assumed away:

- **Acceptance bar:** the base mesh is done when (a) it deforms without pinching/
  collapsing through the full range of the animation clip catalog (idle/walk/run/wave/
  stir poses, checked by eye via render at extreme poses), (b) its silhouette reads as
  "soft toy humanoid" and not "boxes with a subsurf modifier slapped on," judged against
  the LoA-remake/Animal Crossing reference bar via side-by-side renders, and (c) the
  armature/weight setup satisfies `blender/loader.py`'s structural assertions.
- **Approach:** built incrementally via the live Blender/MCP loop — construct a low-
  resolution control cage by hand (scripted), add strategic loop cuts at joints
  (shoulders, elbows, knees, waist) so the subdivision surface holds shape under
  bending, mirror modifier for left/right symmetry, then apply proportional bevels.
  This is standard low-poly-to-subsurf practice, not novel — the risk is execution
  quality via scripting, not the technique itself.
- **Fallback if scripted topology quality is insufficient after reasonable iteration:**
  the existing design bible already documents CC0 skinned base meshes (KayKit /
  Quaternius, via `tools/bootstrap.py`) as a fallback for "if a character ever needs
  skinning." If the from-scratch scripted base mesh doesn't clear the acceptance bar
  above after a bounded number of iteration passes, we fall back to retopologizing /
  adapting one of those pre-existing CC0 bases (still committed as a `.blend`/source
  asset, still re-skinned/re-UV'd to our palette system) rather than continuing to
  fight a from-scratch script. This decision point gets raised to the user explicitly
  if it's hit — it is not silently swapped.

### 2. Archetype variation (scripted, deterministic, data-driven)

This stage is split into separate scripts/modules with single, clear
responsibilities — each independently runnable and testable via its own `result = {...}`
contract over the same headless-Blender invocation pattern:

| Unit | Input | Output | Responsibility |
|---|---|---|---|
| `blender/loader.py` | `base_humanoid.blend` path | in-memory Blender scene | Load the base mesh + armature; assert expected object/bone names exist (fails loud if the base asset drifts from what downstream stages expect). |
| `blender/proportions.py` | archetype spec (bone scale factors / shape-key values) | mutated armature/mesh | Apply archetype-specific proportion changes only. No clothing, no materials, no animation. |
| `blender/clothing.py` | archetype spec (clothing/hair part list, each referencing a part-authoring script or sub-asset) | added mesh objects, bound to armature | Add and bind clothing/hair/prop geometry. Each clothing piece is its own small authored mesh (same bevel+subsurf treatment), not part of the base body mesh. |
| `blender/materials.py` | archetype spec (palette cell assignments) | material slots assigned | Maps existing `palette.py` atlas cells onto UV islands. No new texture painting — same "flat color cell" contract as v1. |
| `blender/animate.py` | archetype's clip list (same catalog names as `animation_contract.py` today: `idle`, `walk`, `run`, `wave`, `stir`) | baked Blender Actions on the armature | Bakes bone-space keyframes for each named clip. Clip *names* are a hard contract (see Godot integration below) — this module is the only place that must know both the old clip-name catalog and Blender's Action-naming rules. |
| `blender/export.py` | fully assembled scene + output path | `assets/generated/<name>.glb` | Calls Blender's native glTF exporter with a fixed, pinned option set (documented in the module itself) and validates the resulting GLB re-imports cleanly before returning success. |
| `blender/validate.py` (new, replaces ad hoc `character_validate.py` checks for characters) | exported `.glb` path | pass/fail + structured report | Runs the new bounding-box/proportion/tri-budget/clip-name assertions (see Testing section) as an automated gate `build.py` calls before declaring success — this is what would have caught the "floating disconnected villager" class of bug automatically. |

Each unit is a plain Python module with a documented function signature and a
`result = {...}` dict return (matching the MCP `execute` protocol's existing
convention so the same code runs identically whether invoked headless via
`blender --background --python` or live against the MCP socket for iteration). A
top-level `blender/build_character.py` orchestrator calls them in the fixed order above
per archetype and is the only thing `build.py` shells out to.

`build.py` continues to be the single entry point (`make assets` / `python3 -m
tools.assetgen.build`); it shells out to headless Blender (invoking
`blender/build_character.py`) for character exports instead of calling the pure-Python
`character_gen.generate()` path.

#### Error handling (new — was previously unaddressed)

- **Blender missing or wrong version:** `build.py` checks for a `blender` executable
  and minimum version (5.0+) before attempting a character build; fails with a clear
  message pointing at `tools/assetgen/README.md`'s new toolchain-dependency section,
  rather than a cryptic subprocess error.
- **Export/validation failure:** `blender/build_character.py` returns a non-zero exit
  code and structured stderr (which part/stage failed) on any error — `bmesh` op
  failure, missing bone name, failed `validate.py` gate — so `build.py` fails the whole
  `make assets` run loudly instead of silently writing a broken `.glb`.
- **Malformed/drifted base asset:** `blender/loader.py`'s name/structure assertions
  (table above) are the guard against `base_humanoid.blend` being edited in a way that
  breaks downstream assumptions.

### 3. Dev iteration loop

While Blender is open with the MCP addon running, the same scripts (or focused
snippets) can be sent to the live `127.0.0.1:9876` socket so proportion/silhouette
work is visible in the user's own Blender window in real time — much faster than the
previous loop (rebuild → Godot import → screenshot → view). This is a development
convenience only; the authoritative, reproducible build path is always the headless
`blender --background --python` invocation, so a machine without a running Blender
GUI (CI, a fresh clone) can still rebuild everything deterministically.

### 4. Migration of Wren and the villager

Both get rebuilt on the new base. **Scope note (splitting concerns per reviewer
feedback):** the pipeline migration (base mesh, armature, archetype system, export,
validation) and Wren's outfit redesign (moving away from "pointy hat + robe"
costume-cliché toward a modern, bohemian, relaxed look — denim shorts, woolen jumper,
layered casual fit — while keeping her recognizably a witch through props: the
Runbook, her jar companion, chalk sigils, rather than costume) are two logically
separate decisions bundled into one migration pass for practical reasons: Wren's
clothing has to be rebuilt as archetype-layer content on the new base regardless of
what it looks like, so redesigning it in the same pass avoids building her old costume
twice. The implementation plan should still track them as separable checkpoints (base
pipeline working with placeholder/simple clothing → Wren's specific redesigned outfit)
so a review checkpoint can land between them if needed.

The villager becomes the second archetype built on the shared base (different
proportions/clothing/hair, same armature rig).

The v1 pure-Python `character_gen.py` / `part_registry.py` / `gltf.py` stay in the repo
(still used for props) but are no longer the path for character generation; their
character-specific registry entries (witch/villager) are removed once the new pipeline
replaces them.

### 5. Testing & validation

Python tests currently assert on our own dataclasses (tri counts, node names) — that
approach doesn't exist once geometry lives in Blender/GLB. New tests (implemented as
the `blender/validate.py` gate from the architecture table, plus pytest wrappers that
invoke it against committed `.glb` outputs):
- Parse the exported GLB directly (JSON chunk, as already done ad hoc during this
  session's debugging) to assert: joint/bone count and names match the expected
  Mixamo-style hierarchy, animation clip names are exactly `idle`, `walk`, `run`
  (looping) and `wave`, `stir` (one-shot) — matching `MOTION_CLIPS`/`GESTURE_CLIPS` in
  `avatar.gd` verbatim (see Godot integration contract below) — and tri count stays at
  or under **1500 tris** per character (same ceiling `character.py`'s `TRI_BUDGET`
  already uses for Wren — carried forward unchanged, not renegotiated by this spec).
- **New: bounding-box/proportion assertions** — e.g. head-height-ratio within an
  expected range, leg mesh spans from hip-joint to foot-joint with no gap — specifically
  to catch the "technically has all the parts but reads as broken/disconnected" class
  of bug that slipped through v1's test suite last time.
- A visual regression aid stays: the `character_gallery.tscn` look-dev scene continues
  to work unchanged (it just instances whatever GLB `build.py` produces).

### 6. Godot integration contract (new — was previously an open question)

`src/player/avatar.gd` hard-codes the clip name catalog: `MOTION_CLIPS` = `idle`,
`walk`, `run` (looping motion states) and `GESTURE_CLIPS` = `wave`, `stir` (one-shot
gestures, triggered via `play_gesture()`, not driven by movement state), matching
Godot's "-loop" import-suffix convention (an animation authored as `idle-loop` imports
as a looping `idle` action; `wave`/`stir` are authored without the suffix and play as
one-shot). This contract does not change:
- `blender/animate.py` must name its baked Blender Actions with the same `-loop`
  suffix convention (`idle-loop`, `walk-loop`, `run-loop`) for the three looping motion
  clips, plus one-shot `wave` and `stir` (no suffix), so Godot's importer produces
  identically-named, identically-looping/one-shot actions post-import — `avatar.gd`
  requires zero changes.
- This gets verified empirically during implementation: import a v2-built `wren.glb`
  into Godot, confirm `AnimationPlayer.get_animation_list()` returns exactly the
  expected 5 names with correct loop flags, before `avatar.gd` is considered
  compatible. If Blender's exporter doesn't honor the naming convention automatically,
  `blender/export.py` renames Actions immediately before export to force it.

## Reproducibility & design-bible alignment (revised policy — was previously hand-waved)

The current design bible's "Asset pipeline" decision record explicitly states:
*"`tools/assetgen` is pure Python (stdlib only)... Blender remains an optional future
tool for character accessory work; it is not a build dependency... Nothing binary is
committed."* This spec directly changes that policy for characters, and the design
bible must be edited (deliberately, per its own stated ritual: *"when this document is
wrong, change it deliberately — docs commit, same ritual"*) as part of implementation,
not left as an implicit tension. Concretely, the decision record's bullets get amended
to:
- Props/nature/buildings: unchanged — pure Python, zero binaries, `tools/assetgen`
  as-is.
- Characters: **Blender 5.0+ becomes a required build-time dependency** for
  `make assets` whenever a character is (re)generated. One binary `.blend` source
  asset per shared base body (e.g. `base_humanoid.blend`) is committed to git — this
  is a deliberate, scoped exception, not a general "binaries are fine now."
  Archetype/clothing/animation variation remains scripted and deterministic on top of
  that committed base.
- The CC0-skinned-base fallback line (KayKit/Quaternius via `tools/bootstrap.py`)
  is retained as the documented fallback *for the base mesh itself* if scripted
  topology doesn't clear the bar (see Feasibility and fallback above) — its role in
  the design bible shifts from "alternative to Blender" to "fallback within the
  Blender-based approach."

"Code-first reproducibility" (pillar 5) is preserved in spirit, redefined precisely:
a fresh clone + `make assets` still deterministically rebuilds every character GLB,
given the committed base `.blend` plus scripted, seeded variation — the same
guarantee as before, just with one additional committed source asset (analogous to a
font file) instead of zero. This redefinition is written into the design bible edit
itself, not left implicit.

## Reference material reviewed

Live-inspected (via the Blender MCP socket, not committed/copied into this repo — used
only for research/proportion grounding) two files from the user's separate
`HammerOfSteel/meshy` project (Meshy-AI-generated assets for a different game, "Seren"):

- `rhys_default_blender.blend` — a Pixar-adjacent stylized character (chibi-ish
  proportions, big expressive eyes, soft rounded shading) wearing almost exactly the
  "woolen jumper + jeans, relaxed/bohemian" register described for Wren's redesign.
  Confirms that register reads well in 3D. Not directly reusable as topology — it's a
  single 270k-tri baked-texture mesh, ~540x our tri budget, wrong tool for our toy-box
  low-poly bar — but validates the clothing/proportion direction.
- `seren_dress_rigged_animated_glb.zip` — confirmed a clean, standard Mixamo-style
  skeleton (see armature section above), proving out the bone-naming/hierarchy
  convention adopted for `base_humanoid.blend`.

These are a different game's assets (different engine target, different art direction,
much higher fidelity) — reviewed for research only, not ported or copied.

## Risks / open questions carried into planning

- Exact bone count/topology detail level is a build-time judgment call, refined via the
  live Blender loop with the user before locking in `base_humanoid.blend` (bounded by
  the acceptance bar and fallback defined above).
- CI/headless build environment needs Blender installed — call out as a new
  toolchain dependency in `tools/assetgen/README.md`, with the version-check error
  handling defined above.
